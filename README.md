# RAG Lab

ต้นแบบระบบ **RAG (ค้นเอกสารด้วยความหมาย + ให้ LLM ในเครื่องตอบจากเอกสาร)** ที่รันในเครื่องตัวเองทั้งหมด ไม่ส่งข้อมูลออกอินเทอร์เน็ต

- ค้น **กฎหมายไทย 36 ฉบับ** (ชุดข้อมูล NitiBench-Statute, 5,127 มาตรา) ด้วยโมเดล embedding `Qwen3-Embedding-0.6B`
- **ถาม AI:** ส่งชิ้นที่ค้นเจอ **4 ชิ้นก่อน ถ้าโมเดลตอบว่าไม่พบจึงขยายเป็น 8 ชิ้น** ให้ LLM ท้องถิ่น (ผ่าน Ollama, ค่าเริ่มต้น `iapp/chinda-qwen3-4b`) ตอบจากแหล่งที่ให้เท่านั้นพร้อมอ้างอิง [n] และตอบ "ไม่พบข้อมูล" เมื่อเอกสารไม่พอ
- **อัปโหลดเอกสารของตัวเอง** (ไฟล์หรือทั้งโฟลเดอร์) แล้วระบบดึงข้อความ → หั่น → สร้างเวกเตอร์ → เพิ่มเป็นจุดบน **แผนที่ความหมาย** และค้นหาเจอทันที
- รองรับ: `pdf` `txt` `md` `csv` `json` `html` `xml` `yaml` `docx` `pptx` `xlsx` และรูปภาพ (`png` `jpg` `tif` `bmp` `webp`) ถ้าเป็นสแกนหรือรูปจะอ่านด้วย OCR (PP-OCRv5 ภาษาไทย)

## ทำถึงไหนแล้ว / ยังไม่ได้ทำ

| ส่วน | สถานะ |
|---|---|
| Retrieval: หั่นเอกสาร, embedding, ค้นหา, แผนที่ความหมาย | ทำแล้ว |
| อัปโหลดหลายชนิดไฟล์, OCR, คลังเอกสารของผู้ใช้ (ลบ/อัปซ้ำได้) | ทำแล้ว |
| Generation: ส่งชิ้นที่ค้นเจอให้ LLM ท้องถิ่นตอบ (`/api/answer`, ปุ่ม "ถาม AI") | ทำแล้ว (แบบพื้นฐาน: ถามครั้งเดียวจบ ไม่มีความจำบทสนทนา) |
| ล็อกแชตขณะลงเอกสาร + สลับการใช้ VRAM ระหว่าง LLM กับ embedding | ทำแล้ว (ดูหัวข้อ "การจัดการ VRAM") |
| **Agent** (วางแผน, เรียกเครื่องมือหลายขั้น, ความจำ) | **ยังไม่ได้ทำ** (ดูหัวข้อ "ต่อยอดเป็น Agent") |

## การใช้งาน

- **แท็บ "ค้นหา · แผนที่":** พิมพ์คำถาม ได้ 10 ชิ้นที่ใกล้ที่สุด แผนที่ซูมไปที่ผลลัพธ์ให้เอง ชี้เมาส์ดูข้อความ คลิกจุดเพื่อปักหมุด ซูมด้วยล้อเมาส์ ลากเพื่อเลื่อน คลิกชื่อกฎหมายด้านล่างเพื่อเน้นกลุ่มนั้น (จุดที่มีวงขาว = เอกสารที่อัปโหลด)
- **แท็บ "โลกบล็อก 3D" (WebGL, สไตล์เกมบล็อก):** ชั้นบนสุดเป็นโลกก้อนลูกบาศก์ แต่ละโซนเนื้อหา (จัดกลุ่มอัตโนมัติจากเวกเตอร์) เป็นไบโอมสีต่างกันมีต้นไม้และลำแสง คลิกไบโอมเพื่อเข้าไปดูเฉพาะจุดในโซนนั้น เป็นเกาะลอยฟ้าที่มีบล็อกลอยอยู่ข้างบน แยกสีตามกลุ่มย่อย ชี้บล็อกดูชื่อ คลิกดูข้อความ และค้นแล้วดูว่าผลลัพธ์อยู่ไบโอมไหน ต้องมีไฟล์ `static/three.module.min.js` (`setup.ps1` โหลดให้ หรือรันเอง: `curl -L -o static/three.module.min.js https://cdn.jsdelivr.net/npm/three@0.160.0/build/three.module.min.js`) ต้องมีอย่างน้อย 60 จุดจึงจะจัดโซนได้ ตำแหน่งไบโอมบนโลกเป็นการประมาณ ไม่ใช่ระยะจริงของเวกเตอร์
- **แท็บ "อัปโหลดเอกสาร":** ลากไฟล์/โฟลเดอร์มาวาง ระบบประมวลผลทีละไฟล์ตามคิว เสร็จแล้วเป็นจุดใหม่บนแผนที่ทันที PDF ตัดสินใจรายหน้า (มีข้อความฝังก็ดึงตรง ถ้าเป็นรูปหรือข้อความน้อยกว่า 50 ตัวอักษรหรือรูปกินหน้า ≥ 20% จึงใช้ OCR) มีคลังเอกสารให้ดูและลบ
- ขีดจำกัด: 100 MB ต่อไฟล์, PDF ไม่เกิน 300 หน้า, ไม่เกิน 5,000 ชิ้นต่อไฟล์, `.doc` `.ppt` `.xls` แบบเก่าไม่รองรับ (ต้องบันทึกเป็น `.docx` `.pptx` `.xlsx` ก่อน)
- **ปุ่ม "ถาม AI":** กดแทน "ค้นหา" เมื่อต้องการให้ LLM สรุปคำตอบ ค้นหา → ส่ง 4 ชิ้นแรกให้โมเดล (ถ้าตอบว่า "ไม่พบ" จะลองใหม่ด้วย 8 ชิ้น) → แสดงคำตอบพร้อมปุ่มอ้างอิง [n] ที่คลิกแล้วกระโดดไปจุดบนแผนที่ **ขณะมีเอกสารกำลังลงคิวอยู่ ปุ่มนี้ถูกล็อก** (ค้นหาธรรมดายังใช้ได้) และปลดล็อกเองเมื่อคิวว่าง

## การจัดการ VRAM (สำคัญถ้าการ์ดจอเล็ก)

ทดสอบบน GPU 6 GB (เดสก์ท็อปใช้ ~1.2–1.9 GB เอง) การอยู่พร้อมกันทั้ง LLM 4B และ embedding ได้แต่เหลือที่น้อยมาก (~460 MiB) ตอนลงเอกสารการ embed เป็นชุดพีคสูงกว่านั้นอีก จึงแบ่งเป็น 2 โหมดที่สลับกันเอง:

| โหมด | LLM (Ollama) | โมเดล embedding |
|---|---|---|
| **ปกติ** (เปิดแอป/รอถาม) | โหลดรอใน VRAM ตั้งแต่เปิดแอป (`keep_alive` 30 นาที) | โหลดเฉพาะตอนต้องแปลงคำค้น แล้วคืน VRAM ทันที (วัดได้ ~2–3 วินาทีต่อคำค้น) |
| **ลงเอกสาร** (คิวอัปโหลดมีงาน) | ถูกคืนจาก VRAM, **ล็อกแชต** | ค้างบน GPU ตลอดทั้งชุด |

พอคิวว่างจะกลับโหมดปกติเอง (โหลด LLM กลับ, คืน embedding) ถ้าต้องการให้ embedding ค้างบน GPU ตลอด (ค้นหาเร็วขึ้น แต่ใช้ VRAM เพิ่ม ~1.2 GB) ตั้งตัวแปร `EMBED_RESIDENT=1` ตัวแปรอื่น: `OLLAMA_URL` (ค่าเริ่มต้น `http://127.0.0.1:11434`), `OLLAMA_MODEL`, `OLLAMA_KEEP_ALIVE`, `ANSWER_STEPS` (จำนวนชิ้นแต่ละรอบ ค่าเริ่มต้น `4,8`; ใส่ `8` = ส่ง 8 ชิ้นรอบเดียว)

## HTTP API (สำหรับต่อกับ Agent)

เซิร์ฟเวอร์ผูกที่ `127.0.0.1` เท่านั้นและ **ไม่มีระบบยืนยันตัวตน** อย่าเปิดสู่ภายนอก

| คำขอ | ผลลัพธ์ |
|---|---|
| `GET /api/search?q=<คำถาม>` | `{"results": [{"i", "score", "law", "section", "user", "text"}]}` 10 รายการ (`law` = ชื่อกฎหมายหรือชื่อไฟล์, `section` = "มาตรา N" / "หน้า N" / "สไลด์ N", `user` = true ถ้ามาจากเอกสารที่อัปโหลด) |
| `GET /api/doc?i=<i>` | `{"law", "section", "text"}` ข้อความเต็มของชิ้นนั้น |
| `POST /api/upload?name=<path/ชื่อไฟล์>` | body = ไบต์ของไฟล์ → `{"job", "name"}` |
| `GET /api/jobs?ids=a,b` | สถานะงานอัปโหลด |
| `GET /api/library` · `POST /api/delete?name=` | รายการ/ลบเอกสารในคลัง |
| `GET /api/points` | ข้อมูลแผนที่ทั้งหมด |
| `GET /api/answer?q=<คำถาม>` | `{"answer", "sources": [{"n", "i", "law", "section", "user", "text"}], "model", "seconds", "tokens", "used_k", "rounds"}` ตอบแบบ adaptive 4→8 ชิ้น (`sources` คือชิ้นที่ใช้ในรอบสุดท้าย `rounds` บอกว่าแต่ละรอบใช้กี่ชิ้นและโมเดลปฏิเสธไหม) ถ้ามีเอกสารกำลังลง จะได้ **HTTP 409** (`"busy": true`) ถ้าเชื่อม Ollama ไม่ได้ได้ **503** |
| `GET /api/status` | `{"available", "ingesting", "pending", "llm_model", ...}` ใช้ตรวจว่าแชตถูกล็อกอยู่ไหม |

ตัวอย่างเรียกจาก Python:

```python
import json, urllib.parse, urllib.request
q = urllib.parse.quote("หลักเกณฑ์การจัดซื้อจัดจ้างภาครัฐ")
hits = json.load(urllib.request.urlopen(f"http://127.0.0.1:8765/api/search?q={q}"))["results"]
for h in hits[:3]:
    print(h["score"], h["law"], h["section"], h["text"][:80])
```

## ต่อยอดเป็น Agent

มี Generation แบบพื้นฐานแล้ว (ถามครั้งเดียวจบ) สิ่งที่ยังขาดสำหรับ Agent (ยังไม่ได้ทำ ไม่ได้ทดสอบ):

1. **ความจำบทสนทนา** และการเขียนคำถามใหม่ให้เจาะจง (query rewriting) ก่อนค้นหา
2. ทำเป็น **เครื่องมือ (tool)** ของ Agent: `search_documents(query)` เรียก `/api/search`, `read_chunk(i)` เรียก `/api/doc` และให้โมเดลวางแผนว่าจะค้นกี่รอบ รุ่น `typhoon2.5-qwen3-4b` ของ SCB 10X รองรับ function calling (ตามหน้าโมเดล ยังไม่ได้ลอง และไม่พบไฟล์ GGUF สำหรับ Ollama ในผลค้นหา)
3. จุดเสียบในโค้ด: `llm_client.ask()` สร้างพรอมต์และเรียกโมเดล, `SearchIndex.search()` ใน `app.py` คืนชิ้นที่ใกล้ที่สุดพร้อมคะแนน, การหั่นอยู่ที่ `SPLITTER` (800 ตัวอักษร ทับซ้อน 100 ถ้าเปลี่ยนต้องสร้าง embedding ใหม่) และขีดจำกัดความยาวคำตอบ `ANSWER_MAX_TOKENS` (450) ปรับได้ใน `llm_client.py`

## ข้อควรรู้ / ปัญหาที่เคยเจอ

- **Path ภาษาไทยทำให้ PaddleOCR พัง** (ยืนยันจากการทดลองควบคุมตัวแปร) ใช้ path อังกฤษล้วน
- **paddle กับ torch อยู่ในโปรเซสเดียวกันบน Windows แล้วชนกันได้** (เจอตอน import paddle ก่อน torch) จึงแยก OCR เป็นโปรเซสลูก อย่านำ `import paddle` ไปไว้ใน `app.py`
- ตอน OCR บน GPU อาจเห็นคำเตือน cuDNN เวอร์ชันไม่ตรงใน log ในเครื่องที่ทดสอบ PP-OCRv5 ยังทำงานได้ปกติ
- **คุณภาพ OCR ภาษาไทย:** PP-OCRv5 อ่านได้ใช้งานได้ แต่มีข้อผิดพลาด เช่น สระ/วรรณยุกต์หาย และตัวอักษรไทยแทรกในคำอังกฤษ จากการทดสอบเล็กๆ (17 คำถาม 11 หน้า) ข้อผิดพลาดแบบนี้กระทบการค้นหาน้อย แต่ **ไม่ใช่การพิสูจน์** สำหรับเอกสารจริงจำนวนมาก
- ข้อความ OCR ที่อ่านผิดจะเข้าไปอยู่ในระบบค้นหาด้วย เอกสารที่ต้องแม่นยำควรให้คนตรวจเทียบต้นฉบับ
- OCR บน CPU ช้า (~10 วินาทีต่อหน้า) บน GPU เร็วกว่าหลายเท่า (ทดสอบ PDF 11 หน้าเสร็จในไม่กี่สิบวินาที)
- **โมเดล `chinda-qwen3-4b` พิมพ์ `<think>` นำหน้าคำตอบเสมอ** แม้ใส่ `think:false` และ `/no_think` เมื่อใช้ `/no_think` มันเปิดบล็อกว่างแล้วตอบต่อโดยไม่ปิดแท็ก `llm_client.strip_think()` จัดการกรณีนี้แล้ว (เคยทำให้ได้คำตอบว่างเพราะตัดทิ้งหมด) ถ้าเปลี่ยนโมเดลให้ตรวจพฤติกรรมนี้ใหม่
- **Ollama บน Windows:** แอปถาดของ Ollama สตาร์ทเซิร์ฟเวอร์ด้วยค่าตั้งของมันเอง และ **ทับตัวแปร `OLLAMA_MODELS`** ในเครื่องที่ทดสอบ (เห็นจาก log ว่าใช้ `C:\Users\…\.ollama\models` ทั้งที่ตั้งตัวแปรเป็นไดรฟ์ D แล้ว) ถ้าอยากเก็บโมเดลไว้ไดรฟ์อื่น ให้ตั้ง "Model location" ในหน้า Settings ของแอปถาด (ในเครื่องที่ทดสอบวิธีนี้ได้ผล)
- คำตอบถูกตัดที่ 450 โทเค็น คำตอบยาว (เช่นคำถามที่ต้องไล่หลายข้อ) อาจจบไม่สมบูรณ์
- **การขยาย 4→8 ชิ้นขึ้นกับว่าโมเดล "ปฏิเสธ" เมื่อข้อมูลไม่พอ ซึ่งไม่น่าเชื่อถือเสมอ:** ในการทดสอบเมื่อส่งแค่ 1 ชิ้น โมเดลยังตอบทุกข้อ (ที่ถูกคือเดาจากชิ้นที่ไม่ตรง) แทนที่จะปฏิเสธ ดังนั้นถ้าคำตอบจริงอยู่ชิ้นอันดับ 5–8 และ 4 ชิ้นแรกพอจะ "ฟังดูตอบได้" โมเดลอาจตอบผิดโดยไม่ขยาย การขยายได้ผลชัดเจนเฉพาะคำถามนอกเรื่อง (ปฏิเสธถูกต้อง) ถ้าอยากให้เห็นชิ้นอันดับ 5–8 เสมอ ตั้ง `ANSWER_STEPS=8` (ยังไม่ได้วัดว่าชิ้นที่ไม่เกี่ยวมากขึ้นทำให้โมเดล 4B สับสนหรือไม่)
- งบหน้าต่างบริบท: `fit_sources()` ตัดชิ้นอันดับท้ายๆ ถ้ายาวเกินงบ (context 4,096 − 450 สำหรับตอบ − เผื่อ 150, ประเมิน 1.6 ตัวอักษรต่อโทเค็น จากที่วัดได้ 1.77 บนชุดกฎหมาย) กรณีชิ้นยาวสุดๆ 8 ชิ้นจึงอาจได้แค่ ~5 ชิ้น
- **บั๊กที่แก้แล้ว:** ก่อนหน้านี้ข้อความของแต่ละชิ้นถูกตัดที่ 420 ตัวอักษรก่อนส่งให้โมเดล (กระทบ 42% ของชิ้นกฎหมาย) ตอนนี้ส่งข้อความเต็ม (สูงสุด 900 ตัวอักษร)

## สิ่งที่ยังไม่ได้ทดสอบ (ตรงไปตรงมา)

- `setup.ps1` **ยังไม่เคยรันครบบนเครื่องสะอาด** (ตรวจแล้วด้วย `-DryRun` และตรวจไวยากรณ์) ถ้าติดขัดตรงไหนแจ้งได้ การติดตั้ง Paddle GPU ใน venv ใหม่แบบ `paddleocr` เปล่าๆ ก็ยังไม่ได้ทดสอบจากศูนย์
- Linux/macOS และโหมด CPU ล้วนของ embedding ยังไม่ได้ทดสอบ
- ตัวอ่าน `docx/pptx/xlsx` ทดสอบกับไฟล์ที่สร้างแบบย่อ ไม่ใช่ไฟล์จาก Word/PowerPoint/Excel จริง ส่วนที่ยังไม่ดึง: หัว-ท้ายกระดาษ กล่องข้อความ คอมเมนต์ ข้อความในรูป
- การเลือกไฟล์/ลากทั้งโฟลเดอร์ในเบราว์เซอร์ ทดสอบผ่าน API เท่านั้น ส่วน UI ของคิวอัปโหลดยังไม่ได้ทดสอบด้วยการใช้งานจริง
- **คุณภาพคำตอบของ "ถาม AI" ยังไม่ได้ประเมินอย่างเป็นระบบ** ทดสอบแค่ไม่กี่คำถาม (ตอบถูกมาตรา และตอบ "ไม่พบข้อมูล" เมื่อไม่มีในแหล่ง) ยังไม่ได้ตรวจว่าเลขมาตราที่อ้างตรงกับต้นฉบับทุกครั้ง ควรทำชุดคำถามทดสอบพร้อมเฉลยก่อนนำไปใช้จริง
- ทดสอบการสลับโหมด VRAM บน RTX 4050 (6 GB) กับ `chinda-qwen3-4b` เท่านั้น โมเดลหรือการ์ดอื่นต้องวัดใหม่ และยังไม่ได้ทดสอบกรณี VRAM ล้น (ผมเข้าใจว่า Ollama จะย้ายบางเลเยอร์ไป CPU เองแล้วช้าลง แต่ไม่ได้ลองจริง)
- `setup.ps1` ไม่ได้ติดตั้ง Ollama และไม่ได้ดึงโมเดลแชต
